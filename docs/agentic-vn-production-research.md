# Agentic visual novel production: capability research and proposed toolset

Status: research and design proposal, 2026-11-09. This is not an implementation plan approved for execution. The scope is the complete production of sophisticated visual novels, including capabilities that do not exist in Storyfella today. Studio and Atelier are products for people as well as agents; new domain features should serve both.

## Findings and evidence

The most important finding is that an MCP interface alone will not make the current apps into an autonomous production pipeline. The work divides into: exposing existing domain operations; extracting operations currently tied to app state; implementing missing authoring, image, playback and delivery capabilities; and building a reliable visual feedback loop. Quality is an iterative production property, not an output promised by any single tool or model.

Evidence labels below: **implemented** means code was inspected, not that every path was executed; **partial** means a relevant implementation exists but does not meet the proposed end-to-end capability; **proposed** means design work is needed. Tests cited are existing tests inspected, not tests run for this investigation. No paid model generation or hands-on app acceptance was performed.

## Production workflows and capability requirements

### Creative direction and continuity

A project should hold an editable, versioned story bible (premise, setting, chronology, characters, relationships, motivations, voice, facts, unresolved decisions and citations to story scenes) and visual bible (style, palette, image specifications, canonical character references, wardrobe, locations and exclusions). Separate hard constraints from suggestions; attach scope, confidence and revision provenance. Allow retrieval by scene, character, location, chronology, dependency and semantic search with bounded context and source links. Agents must be able to propose, compare, revise and supersede decisions; humans need the same views in Studio. Treat retrieved text and imported references as untrusted creative data, not instructions to the agent.

Requirements: structured entries and links; exact and fuzzy search; selective context packs; explicit canonical versions; contradictions flagged as suggestions with evidence, not automatically rewritten. New data model and UI are needed; current artifact descriptions are useful but are not a full production bible.

### Story design and writing

Support outline, scene graph and chapter management; create and revise source ranges, scenes and dialogue; resolved rename; story-to-asset mapping; conditional choices and route intent; continuity queries; route summaries and ending requirements; diff/preview/apply; and validation with source locations. Existing language services can power the first version. Define exact edits with source version/content hash, UTF-8 coordinate rules and source map across includes. Preserve trivia and user edits. Existing writing review and sessions in `crates/studio-core/src/workflows/` are worth reusing after checking their behavior per use case.

Extend narrative semantics based on concrete VN requirements: typed variables, bounded numbers, enumerations and strings; expressions with defined types and errors; conditional text/choices; reusable sequences; inventory and relationship state as abstractions over general state; deterministic random behavior only with explicit seed and persisted state; optional narrative time. Do not promise unrestricted scripting: it hurts analysis, replay and portability. Design scene transitions, fallthrough and choice continuation explicitly. Version plan and save formats; define migration and failure behavior when a story changes. Scalable analysis should use bounded state exploration and distinguish unreachable graph nodes from paths infeasible under actual flag values.

### Asset planning and consistency

Model character identities, references, character sheets, poses, expression/outfit/accessory combinations; locations with time, weather, viewpoint, lighting and state; props, CGs, overlays and UI graphics. Track desired versus existing vs used, ownership, revision, dimensions, anchor, alpha, framing, usage rights/provenance, and dependencies. A coverage matrix should calculate required combinations from authored story use and explicit production requirements; batch creation must permit per-item retry and stop conditions.

Layered characters are a proposed app/runtime feature: stable canvas and anchor, named compatible layers, ordering and compositing rules, expression/wardrobe selectors and a renderer shared by preview and player. Not every generated image can safely be decomposed; support full sprite alternatives and hand-painted assets. Warn when variants differ in dimensions, head/eye position, alpha, scale or silhouette, but treat visual similarity as advisory rather than identity proof. Provide contact sheets and matched crops for human or VLM review.

### Image operations without external scripts

All operations should use explicit coordinate systems, dimensions, pixel format, alpha semantics and revision IDs, return visually inspectable previews, and be undoable or produce new revisions. Include numerical primitives and higher-level workflows:

* Inspect image dimensions, profile, alpha, bounds, metadata, histogram and pixel coordinates; preview full image, tiles, zoomed crops, checkerboard, mask overlays, side-by-side and differences.
* Crop and reset non-destructively; resize image with specified resampling; resize artboard separately from scaling; fit/fill; pad; extend canvas with anchoring; rotate, mirror, align and distribute. Content-aware extension is separate from adding transparent pixels.
* Create, combine and transform masks from rectangles, polygons, brush paths, alpha and imported masks; invert, intersect, subtract, feather, dilate/erode; inspect coverage. Semantic/point/box selection and background removal require a suitable segmentation capability, confidence, editable result and fallback. Current rectangle and painted masks are useful foundations, not these complete features.
* Composite and manage layers/groups, visibility, opacity, transforms and masks; add/replace image layers; control alpha and edge cleanup; extract a selection to a layer or artboard; export at specified size and format. Preserve original pixels and safe recovery.
* Generate, edit, inpaint and outpaint with explicit source, ordered references, masks, provider capabilities, size, seed where supported, and preserved regions. Record requested and effective parameters and provenance; do not imply seed guarantees reproducibility across providers or versions.

A visual model should be able to request a region in normalized coordinates or image pixels; server responses must identify orientation, reference size and transforms so an agent can map its visual selection accurately. Guard against oversized image replies with thumbnails, region requests and bounded pagination.

### Scene direction and player experience

Author backgrounds, layered sprites, expressions, screen anchors, transforms, depth, dialogue UI, scene transitions, timed effects, camera, CGs and overlays. Preview with the actual runtime renderer, dialogue and safe areas at target resolutions. Provide visual comparisons and checks for cropped heads, obscured faces, unreadable text, inconsistent sprite registration and alpha artifacts. Current AST and runtime implement staging, swap, hide and limited directions; camera motion, animation, transitions and rich presentation require extending the complete pipeline.

Add sound and music tracks, voice lines, cues, mixing, subtitles, transitions and timing with deterministic authored semantics; support human recordings and model-generated assets. The runtime must separate event/timing semantics from audio devices, and save/restore should account for timed state. Plan menus, backlog, rollback, skip/read state, autoplay, settings and gallery as product features, with appropriate player control.

Localization needs stable string identifiers, context, pluralization/formatting, translated UI and optional localized images/audio, plus layout checks. Ren'Py's [translation documentation](https://www.renpy.org/doc/html/translation.html) illustrates the range of assets that may need localization. Accessibility needs keyboard/controller navigation, adjustable text and contrast, captions for meaningful audio, reduced motion, screen-reader support where feasible, and validation against target platform requirements; [WCAG 2.2](https://www.w3.org/TR/WCAG22/) is useful guidance, not an automatic certification for a desktop game.

### Playtest, quality and release

Add an isolated preview session tied to an immutable compiled plan and asset revisions. Commands: start, advance, select, inspect state/events, checkpoint, restore, jump with explicit state semantics, stop, capture frame and batch capture. Report current source location and exact rendered asset revisions. Support reproducible route scripts, seeded tests, coverage reports for scene/choice/ending/asset and state combinations, bounded traversal, loop limits and a clear indication of what was not tested. Static graph analysis cannot prove semantic reachability; dynamic coverage cannot prove all paths without exhaustive state exploration.

Quality checks should combine deterministic checks (missing assets, broken links, dimension mismatch, clipping against measured bounds, overlong text, dead ends, bad audio metadata) with advisory VLM/LLM reviews (anatomy, continuity, tone, pacing). For subjective issues return evidence, confidence and reproduction path. Provide a queue of review findings and a way to resolve or waive with rationale. Human playtests and editorial judgment remain necessary to establish narrative and visual quality.

Release tooling needs dependency closure, portable project/export paths, repeatable builds, asset and model provenance, license records, localization and accessibility reports, platform-specific player packaging, and smoke tests on each target. Do not silently bundle credentials, internal prompts, drafts or private references. Version and verify packaged artifacts; distinguish project authoring save from distributable build.

## Proposed MCP contract

Expose a coherent project-oriented service. Names below are illustrative capabilities, not a demand for hundreds of separate tools. Prefer typed operations and documented schema over free-form action strings; split endpoints when schemas or risk differ materially. Offer capabilities in discoverable groups and pagination/filtering so a model is not flooded by the entire API.

| Group | Suggested operations | Core inputs and outputs |
| --- | --- | --- |
| Project | `project.open`, `project.inspect`, `project.capabilities`, `project.changes` | Project handle, version, permissions, supported operations, change cursor. No implicit globally active project. |
| Bible | `context.query`, `canon.upsert`, `canon.relate`, `canon.audit` | Scoped facts/references, source provenance, version, selected context and contradictory claims. |
| Story | `story.inspect`, `story.graph`, `story.edit`, `story.validate`, `story.references` | Scene/source identifiers, expected source version, typed edits, diagnostics and resulting version/diff. |
| Assets | `asset.list`, `asset.create`, `asset.update`, `asset.variants`, `asset.coverage` | Stable UUIDs, typed metadata, base/variant relationships, expected registry version and filtered coverage. |
| Artwork | `artboard.inspect`, `artboard.edit`, `image.inspect`, `mask.edit`, `artwork.render`, `artwork.publish` | Explicit artboard/layer/mask IDs and coordinate frame; immutable result, preview, revision and conflict details. |
| Generation | `generation.capabilities`, `generation.submit`, `job.get`, `job.list`, `job.cancel`, `candidate.review` | Snapshot of request and references, idempotency key, job ID, status, progress, candidate IDs and effective settings. Batch returns per-item status. |
| Direction | `scene.stage`, `scene.preview`, `scene.audit` | Scene/beat and revision, staged items and constraints, rendered frame plus annotations and findings. |
| Testing | `play.start`, `play.step`, `play.inspect`, `play.checkpoint`, `play.capture`, `test.explore`, `test.report` | Plan identity and isolated session, actions/events, screenshot, reproducible route and bounded coverage. |
| Delivery | `release.validate`, `release.build`, `release.inspect` | Explicit target and manifest, findings, artifact IDs and reproducible build information. |

Use resources for immutable source snippets, image revisions, review reports and manifests where supported; tool outputs should include structured metadata and actual MCP image content for thumbnails/crops as supported by the client. Provide bounded tool-based image retrieval for clients lacking resource support. Agentkit already maps structured metadata at the MCP boundary. Preserving native image blocks alongside it requires an adapter change and client verification. Let the agent request focused crops and comparison sheets. Keep any required image transfer within the client's supported MCP capabilities.

Long operations must return quickly with persisted job identifiers and status polling even if an optional MCP tasks extension is unavailable. Capability-negotiate progress and task support. Record jobs before external side effects; make idempotency keys scoped to project and operation; distinguish cancellation requested, provider cancellation confirmed, and result attachment stopped. Retries must not silently double-submit paid generation. Retain successful outputs when attachment fails and show how to recover. Define retention, quotas, ownership, partial failures, and cleanup.

Writes must require expected revision or an explicit merge strategy. A conflict returns current versions and a useful diff; do not overwrite dirty app state. Batch operations declare atomicity per operation and report each outcome. Support preview/dry-run where meaningful; undo is domain-aware, not a substitute for revision checks. Explicit project handles and capability scopes prevent accidental cross-project edits. Local stdio is a good initial deployment; any network server needs explicit authentication, authorization, origin validation, bounded uploads, and safe path handling. Tool annotations are hints, not an authorization mechanism.

## Architecture and coordination decisions

1. Extract Atelier's document/edit/render/generation domain into a UI-independent library or service with stable commands and validation, reusing the GUI's logic rather than independently rewriting it. Keep platform rendering parity explicit; ensure image outputs can be produced headlessly or report limitations. Preserve document schema and editable work.
2. Have one authoritative project coordination layer for GUI and agent commands. Decide explicitly between an app-owned service (can respect unsaved state but depends on app lifecycle) and a separate project service (works headlessly but needs explicit dirty-document synchronization). A hybrid is possible only with a defined owner/lease, change stream and conflict protocol. Do not silently mutate files behind open editors.
3. Preserve Studio's `save_authoring_checked` and source-intent recovery, catalog checked versions, Atelier expected artwork baselines, and document-save-before-publication semantics. MCP must surface saved-document/publish-failed as a partial result, not erase it with a generic failure.
4. Reuse `agentkit-mcp` where compatible, but assess its synchronous registry, text-only result abstraction and advertised capabilities against required images, asynchronous execution, progress and resources. Extend shared Agentkit only for genuinely reusable protocol capabilities; put VN domain behavior in Storyfella. Test real client interoperability rather than relying on a specific host's extensions.
5. Version external schemas independently from project, document, story plan and save formats. Use stable IDs for artboards and layers, canonical pixel coordinates, project-scoped handles, explicit resource lifetimes and migration paths. Artboard IDs currently use numeric IDs and layer operations often use indexes; durable identity across reordering and concurrent edits needs investigation and design.
6. Provider capability discovery must reflect actual configured model and backend, not just a vendor label. Separate deterministic pixel operations from generative operations, including their reproducibility, cost and quality expectations.

## Prioritization and acceptance

**Phase 0 — Evidence and architecture.** Trace all code paths and stale documentation, inventory exact live app features, make a capability matrix backed by tests, decide owner/lease and protocol integration, build an isolated fixture project. Verify runtime constraints, dirty editors, queue restart behavior and client image rendering.

**Phase 1 — Minimum agentic vertical slice.** Project open/inspect; safe source and catalog edits; image generation and candidate review; crop/mask/layer basics; publish accepted art; deterministic preview and screenshots. Scenario: create a three-character, two-location branching chapter with a persistent flag; create multiple expressions, revise a masked region, bind art, exercise both choices, inspect rendered frames, save/reopen and detect a concurrent edit. No shell or ad hoc script is needed by the agent. Include app restart and failed generation/attachment recovery.

**Phase 2 — Scale and quality.** Durable batches, production bible, asset coverage, comparison/contact sheets, stronger selection and background removal, sprite registration, quality findings and route exploration. Evaluate on a larger fixture with explicit scene, variant and resolution counts; measure successful asset coverage, rework, visual consistency judged blindly by reviewers, tool-call count, latency and cost. Establish baselines rather than inventing quality thresholds.

**Phase 3 — Expressive VN and shipping.** Extend language/runtime and app UI for richer state, compositing, transitions, audio, localization, accessibility and packaging, delivering each capability end to end with migrations and tests. Add advanced character layering and visual editing as warranted by measured workflows.

Verification matrix: unit tests for transformations and protected pixels; integration tests for cross-app saves and optimistic conflicts; protocol tests for schemas, image blocks and failure responses across at least two independent MCP clients; end-to-end tests of an actual creative task with representative vision models; crash/retry tests; golden screenshot tests at multiple aspect ratios; route/coverage correctness tests; and human review of generated work. Run real provider and GPU acceptance separately from deterministic offline tests and record model/version/settings, limitations and costs.

## Open decisions and limits

Questions requiring product decisions include target platforms and distribution, acceptable project scale and hardware/cost budgets, local versus remote operation, user control over automatic candidate acceptance, project collaboration model, release and localization priorities, and which image models/segmentation backends can meet consistency needs. These should be informed by the vertical slice rather than treated as prerequisites for investigating the system.

This research inspects representative implementation paths, data structures and test coverage. Verify each proposed operation against current code, tests and controlled execution. The [architecture and chapter contract](agentic-vn-production.md) records the implementation decisions and first acceptance evidence.
